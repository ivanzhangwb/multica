Multica 仓库可视化总览

把编码 Agent 变成真正的团队成员

这份页面基于仓库中的 README、产品全景文档和 monorepo 结构整理，目的不是复述所有细节，而是把项目最核心的产品定位、工作流、技术结构和代码组织方式压缩成一张能快速读懂的地图。

开源 Managed Agents 平台 人类与 AI 共用同一工作流 厂商中立，支持本地与云端运行时

一句话判断项目本质

Multica 不是单点的 AI 工具，而是一个让 issue、agent、runtime、skill 和协作流程联动起来的任务操作系统。

工作入口是 Issue 任务分配、评论讨论、状态推进、通知订阅都围绕 issue 展开。
执行主体是 Agent Agent 像人一样拥有身份、配置、技能、对话历史和运行状态。
执行环境是 Runtime 本地 daemon 或云端实例负责发现可用 CLI 并实际跑任务。

Fast Facts

项目核心指标

从仓库与文档里可以快速提炼出几个最能定义 Multica 轮廓的数字。

11 支持的 Agent CLI Claude Code、Codex、Copilot CLI、Gemini、Kimi、Kiro CLI 等统一接入。

Product Map

六个必须先理解的核心对象

只要理解这六个对象之间的关系，就能读懂大多数功能设计和代码组织。

Container

Workspace

所有资源的租户边界。Issue、Agent、Skill、Project、成员、通知全部隔离在 workspace 内。

Work Unit

Issue

最核心的工作单元。它既是任务看板项，也是讨论线程、状态机、订阅中心和协作上下文。

Worker

Agent

带身份的 AI 工作者。可被指派、可发表评论、可创建 issue，也能绑定技能、环境变量和 MCP 工具。

Compute

Runtime

真正执行任务的机器环境。由 daemon 上报能力，告诉平台这台机器能跑哪些 agent CLI。

Memory

Skill

工作区级复用知识。过去解决过的问题会沉淀成可挂载的说明文档，成为 agent 的长期能力。

Automation

Autopilot

按 cron 或 webhook 自动创建 issue 并分配给 agent，让固定流程不再依赖人手触发。

Flow

产品最短工作流

README 里的快速上手可以压缩成下面四步，这也是用户第一次感知产品价值的最短路径。

1

连接 Runtime

运行 multica setup，本地 daemon 启动并向平台注册一台可执行任务的机器。

2

创建 Agent

为 agent 选择 provider、runtime、指令、环境变量和技能，形成一个可持续复用的 AI 身份。

3

指派 Issue

像指派给同事一样把 issue 指给 agent，它会自动认领任务、开始执行并更新状态。

4

在同一线程协作

进度、阻塞、结果都回到 issue 评论中；继续 @agent 会触发下一轮任务，形成可追溯闭环。

Architecture

系统架构与责任分层

Multica 的架构重点不在“模型能力”本身，而在任务编排、执行可见性与多主体协作的一致性。

产品与数据平面

前端界面：Next.js + 桌面壳 Web 端与 Electron 桌面端共享大部分产品体验，桌面端补充多标签与原生能力。
服务端：Go + WebSocket 负责 issue、comment、project、agent、runtime、notification 等核心领域与实时事件流。
数据库：PostgreSQL + pgvector 保存多态 actor 模型、任务历史、聊天记录、技能文件与订阅关系。

执行与扩展平面

Daemon 驻留在用户机器上，自动发现 codex、claude、gemini 等 CLI。
Skills 作为附加上下文注入 agent 工作目录，帮助任务跨 issue 复用经验和流程。
MCP Servers 按 agent 粒度接入外部工具，让执行环境从“能写代码”扩展到“能调系统”。

README 中给出的主架构为：Next.js 前端 + Go Backend + PostgreSQL + Agent Daemon。产品全景文档进一步说明，绝大多数行为都围绕“多态行动者” 设计，即成员和 agent 共享同一套行为模型。

Repo Map

Monorepo 结构怎么读

如果目标是快速上手代码，不需要一开始就通读所有目录。先记住下面这几个高价值入口。

应用层目录

apps/web 主产品 Web 端，承载 issue board、settings、chat、workspace 等核心界面。
apps/desktop Electron 桌面端，为同一产品模型提供本地壳、窗口与桌面体验。
apps/docs 文档站点，用于对外说明安装、CLI、自托管与产品能力。

共享与后端目录

packages/views / packages/ui 共享视图与 UI 层，承接跨应用的页面片段和组件系统。
packages/core 通用逻辑、类型或领域级工具，作为应用和视图层的基础依赖。
server Go 后端、sqlc 查询、迁移、命令行与 agent 执行适配器的集中所在。

Visual Anchor

产品界面的核心感知

从这张界面图里能读出的设计判断

Agent 不是隐藏在弹窗后的执行器 它被放进和人类成员同等级的任务分配与评论体系里。
协作入口是项目管理，而不是聊天窗口 用户首先看到的是 board、issue、timeline，而不是单轮 prompt 输入框。
平台价值在于编排与持续性 同一 agent 在同一 issue 中可恢复会话、保留工作目录，并持续积累技能。

Ops

最值得记住的命令与入口

对新人来说，理解这几个入口比记住所有文档细节更重要。

用户侧命令

multica setup 配置、认证并启动 daemon，是连接本地 runtime 的最短路径。
multica daemon status 确认 daemon 是否在线，以及当前机器是否正常作为 runtime 汇报。
multica issue create 创建任务，随后即可在 UI 或 CLI 中分配给 agent。

开发侧入口

make dev 仓库推荐的一键开发启动命令：建环境、装依赖、配数据库、跑迁移并起服务。
pnpm test / pnpm lint monorepo 顶层统一测试与静态检查入口，内部通过 Turbo 编排执行。
server/cmd/multica CLI 的 Go 实现入口，和 runtime / issue / project 等命令编排直接相关。

Bottom Line

最终结论

如果只保留一句总结，应该是下面这句。

Multica 的竞争点不只是“能调几个模型”

它把 Agent 放进了真实团队流程 任务创建、分配、执行、通知、历史追踪、自动化和技能复用都统一在一个工作系统里。
它把执行能力和产品体验分离 底层 CLI 可以替换，甚至运行时也可替换，但上层协作模型保持稳定。
它是一个“多主体任务操作系统” 真正的产品价值在于把人、agent、runtime、skill、project 和 issue 组织成一套长期运行机制。
